Topic 1 · Handler class pattern

The trigger delegates, the handler decides

Keep the trigger itself thin. It should only route each event to a method on a handler class — nothing else.

trigger AccountTrigger on Account (
    before insert, before update, after insert, after update
) {
    AccountTriggerHandler handler = new AccountTriggerHandler();

    if (Trigger.isBefore) {
        if (Trigger.isInsert) handler.beforeInsert(Trigger.new);
        if (Trigger.isUpdate) handler.beforeUpdate(Trigger.new, Trigger.oldMap);
    }
    if (Trigger.isAfter) {
        if (Trigger.isInsert) handler.afterInsert(Trigger.new);
        if (Trigger.isUpdate) handler.afterUpdate(Trigger.new, Trigger.oldMap);
    }
}
public class AccountTriggerHandler {

    public void beforeInsert(List<Account> newAccounts) {
        for (Account acc : newAccounts) {
            if (acc.Industry == null) {
                acc.Industry = 'Other';
            }
        }
    }

    public void beforeUpdate(List<Account> newAccounts, Map<Id, Account> oldMap) {
        // validation and defaulting logic lives here
    }

    public void afterInsert(List<Account> newAccounts) { /* ... */ }
    public void afterUpdate(List<Account> newAccounts, Map<Id, Account> oldMap) { /* ... */ }
}
Topic 1 · Handler class pattern

Why bother with a handler class?

Single entry point

One trigger per object means one predictable place to look when something goes wrong.

Directly unit testable

Call handler.beforeInsert(records) straight from a test — no need to insert through the trigger.

Easy to review

A reviewer can read beforeUpdate() on its own, without untangling it from trigger plumbing.

Reusable methods

The same validation or defaulting logic can be called from a batch job or an invocable method too.

The rule underneath it all

Salesforce recommends exactly one trigger per object. Every event for that object funnels through it, and the handler class is where the real logic — and its growth — lives.

Topic 2 · Bulkification

The problem: SOQL and DML inside a loop

This looks harmless with one record — but Trigger.new can hold up to 200 records at once.

trigger OpportunityTrigger on Opportunity (after update) {
    for (Opportunity opp : Trigger.new) {
        // ❌ SOQL query runs once per record
        Account acc = [SELECT Id, Last_Opportunity_Date__c
                        FROM Account WHERE Id = :opp.AccountId];

        acc.Last_Opportunity_Date__c = opp.CloseDate;

        // ❌ DML statement runs once per record
        update acc;
    }
}

What breaks, and when

With 1 record this runs fine. With 200 records — a routine bulk update — it issues 200 queries and 200 DML statements, blowing past the 100-query and 150-DML-statement limits per transaction. The entire save fails, for every record.

Topic 2 · Bulkification

The fix: collect, query once, update once

Same outcome, but the query and DML counts no longer grow with the batch size.

trigger OpportunityTrigger on Opportunity (after update) {
    // 1. Collect every Account Id the batch touches
    Set<Id> accountIds = new Set<Id>();
    for (Opportunity opp : Trigger.new) {
        accountIds.add(opp.AccountId);
    }

    // 2. One SOQL query for the whole batch
    Map<Id, Account> accounts = new Map<Id, Account>(
        [SELECT Id, Last_Opportunity_Date__c FROM Account WHERE Id IN :accountIds]
    );

    // 3. Build the update list, then one DML statement
    List<Account> toUpdate = new List<Account>();
    for (Opportunity opp : Trigger.new) {
        Account acc = accounts.get(opp.AccountId);
        if (acc != null) {
            acc.Last_Opportunity_Date__c = opp.CloseDate;
            toUpdate.add(acc);
        }
    }
    update toUpdate;
}
Topic 2 · Bulkification

Anti-pattern vs. bulk-safe

❌ Anti-pattern

  • SOQL query inside the for loop
  • DML statement inside the for loop
  • Cost scales with the number of records
  • Works in testing, fails on real bulk data

✓ Bulk-safe

  • Ids collected into a Set first
  • One SOQL query, using a Map for lookup
  • One DML statement for the whole batch
  • Cost stays flat from 1 record to 200

Governor limits a loop-based trigger tends to hit

Limit (per transaction)SynchronousWhy it matters here
SOQL queries100Hit instantly once a query sits inside a loop
DML statements150Same problem, on the write side
DML rows10,000Usually fine if the DML itself is bulkified
CPU time10,000 msRepeated query/DML overhead adds up fast
Topic 3 · Recursion control

How a trigger re-triggers itself

A trigger updating its own object — directly or through a Flow — can restart the save sequence from the top.

Why this matters: each re-entry re-runs the full order of execution for that record, which can duplicate side effects, waste limits, or in the worst case recurse until a governor limit is hit.

Topic 3 · Recursion control

Guarding with a static variable

A static variable lives for the length of one transaction — exactly the scope a recursion guard needs.

public class AccountTriggerHandler {
    // Persists for the whole transaction, resets on the next one
    private static Boolean hasRunAfterUpdate = false;

    public void afterUpdate(List<Account> newAccounts, Map<Id, Account> oldMap) {
        if (hasRunAfterUpdate) return;
        hasRunAfterUpdate = true;

        // logic that updates related records, which might
        // indirectly cause this same trigger to fire again
    }
}

Need record-level precision instead?

Swap the Boolean for a static Set<Id> processedIds and add each record's Id after it's handled — useful when some records in a batch legitimately need to run twice and others don't.

Wrapping up

Good habits for production-ready triggers

One handler per object

Keep the trigger thin; let the handler class hold and organize the logic.

Bulkify everything

Collect Ids, query once outside the loop, then issue one DML statement.

Guard against recursion

A static Boolean or Set<Id> stops a trigger from re-entering itself mid-transaction.

Keep methods small

Each handler method should do one job, so it stays easy to test and to read.

Key takeaways

A handler class turns a trigger into testable, reviewable code. Bulkifying means no SOQL or DML ever sits inside a loop over Trigger.new. And a static-variable guard keeps a trigger from restarting the order of execution on itself. Together, these three habits are what separate a demo trigger from a production one.
