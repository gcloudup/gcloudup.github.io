Topic 1 · Trigger syntax

A trigger's basic shape

A trigger is declared on one object, for one or more events, inside a single trigger block.

trigger AccountTrigger on Account (before insert, before update, after insert, after update) {
    if (Trigger.isBefore && Trigger.isInsert) {
        // runs once, for the whole batch of new Accounts
        for (Account acc : Trigger.new) {
            if (acc.Industry == null) {
                acc.Industry = 'Other';
            }
        }
    }
}

One trigger per object

Salesforce recommends a single trigger per object, with the logic organized inside it or delegated to a handler class.

List the events you need

Only the events named in the trigger definition will fire it — nothing else runs silently.

Always bulk-safe

Trigger.new is always a List, even for a single record, so loop over it rather than assuming one record.

Topic 1 · Context variables

Trigger.new vs. Trigger.old

Both are collections of the sObjects being processed — the difference is which version of the record they hold.

  • The new or incoming version of each record
  • Populated for insert, update and undelete
  • Editable only in before triggers
  • Read-only once inside an after trigger
  • The record as it was before the change
  • Populated for update and delete only
  • Always read-only
  • Useful for comparing old vs. new field values

Tip: Trigger.newMap and Trigger.oldMap give the same records keyed by Id — perfect for fast lookups by Id inside the trigger.

Topic 2 · Before vs. after

Before triggers vs. after triggers

◐ Before

  • Runs before the record hits the database
  • Edit Trigger.new directly, no DML needed
  • Best for validation and default values

◑ After

  • Runs after the record already has an Id
  • Records are read-only; requires new DML
  • Best for related records and callouts

Topic 2 · Before vs. after

Insert, update, delete & undelete in practice

trigger OpportunityTrigger on Opportunity (
    before update, after update, after delete, after undelete
) {
    if (Trigger.isBefore && Trigger.isUpdate) {
        for (Opportunity opp : Trigger.new) {
            Opportunity oldOpp = Trigger.oldMap.get(opp.Id);
            if (opp.StageName == 'Closed Won'
                && oldOpp.StageName != 'Closed Won') {
                opp.CloseDate = Date.today();
            }
        }
    }
    if (Trigger.isAfter && Trigger.isUndelete) {
        // Trigger.new is populated again on restore
        System.debug('Restored: ' + Trigger.new.size());
    }
}

Delete

Only Trigger.old is populated. There is no new version of a record being removed.

Undelete

Restores a record from the Recycle Bin. Trigger.new is populated again, with a new Id in some cases.

Compare old vs. new

Trigger.oldMap.get(id) is the standard way to read the previous value of a field inside an update trigger.

Why this matters: a Flow or a second trigger updating the same record can start this whole sequence over again — this is how recursive trigger bugs happen.

Wrapping up

Good habits for your first triggers

One trigger per object

Keep a single trigger and move logic into a handler class as it grows.

Match logic to the stage

Validate and default in before; touch related records in after.

Always think in bulk

Loop over Trigger.new — never assume exactly one record is being processed.

Watch for recursion

Guard against a trigger re-triggering itself through Flow or DML on the same object.

Key takeaways

Trigger.new and Trigger.old give you the record before and after the change. Before triggers edit for free; after triggers need DML. Every save follows the same order of execution — understanding it is what makes complex Apex predictable.
