Topic 1 · Architecture

Multi-tenancy: one building, many apartments

Many customers (tenants) share the same infrastructure and code, while each customer's data and configuration stays private.

Shared building

Servers, databases and the platform code are shared, so Salesforce upgrades everyone at once. There are three major releases a year.

Private apartment

Your org is isolated. Each record and setting is tied to your org, so other customers never see your data.

Shared utilities

Because resources are shared, no one may hog them. Governor limits keep every tenant fair.

Topic 1 · Architecture

Metadata-driven and governed

Objects, fields, page layouts, flows and Apex classes are all metadata. The platform's runtime engine reads that metadata to build screens, enforce rules and run your logic. When you deploy, you are moving metadata from one org to another.

Topic 2 · Orgs & environments

What is an org?

An org is your own private Salesforce environment, with its own data, users and customizations. There are several kinds.

What
The live org where real users and real customer data live.
Use it for
Running the business. Never build or test directly here.
What
A free, full-featured org for learning and experimenting, with sample data and no link to production.
Use it for
Practice, tutorials, Trailhead and personal projects. This is the org we use today.
What
A copy of your production org, created from production.
Use it for
Developing, testing and training away from live data, before deploying to production.
What
A short-lived, disposable org created from a configuration file using the Salesforce CLI. It lasts 7 days by default and up to 30.
Use it for
Source-driven development, automated testing and CI pipelines.

Developer sandboxBuild and unit test your change.
→
QA / integrationTest with more data alongside other changes.
→

Changes move between environments using change sets, the Salesforce CLI or DevOps Center. Rule of thumb: always build in a sandbox or scratch org, never directly in production.

Topic 3 · Developer tools

Your toolbox

Click a tool to learn what it is for.

Setup
What: The browser-based admin area. Best for: creating objects, fields, users and flows without code.
Developer Console
What: A lightweight IDE inside Salesforce. Best for: running quick Apex, testing SOQL queries and reading debug logs.
VS Code + Salesforce Extension Pack
What: The main professional editor for Apex and Lightning Web Components. Best for: everyday development, source control and deploying to orgs.
Salesforce CLI (sf)
What: A command-line tool. Best for: creating orgs, retrieving and deploying metadata, running tests and automating pipelines.
Code Builder
What: VS Code in the browser with the Salesforce tooling already set up. Best for: developing with nothing to install locally. Availability depends on your edition.
Topic 3 · Developer tools

Clicks or code?

There are two ways to build on Salesforce. Pick a side to compare.

Tools
Flow, validation rules, formula fields, page layouts, reports and dashboards.
Strengths
Fast to build, admin-friendly and easy to maintain.
Choose it when
The requirement can be met with built-in features. This is the default choice.
Tools
Apex classes and triggers, Lightning Web Components, REST callouts.
Strengths
Full flexibility for complex logic, custom interfaces and integrations.
Choose it when
Clicks cannot handle the logic, scale or user experience you need.

Rule of thumb: clicks before code.

Topic 4 · Dev environment

Run your first Apex

  1. In your org, click the gear icon and open Developer Console.
  2. Choose Debug, then Open Execute Anonymous Apex Window.
  3. Paste the code below, tick Open Log and click Execute.
System.debug('Hello, Salesforce!');

List<Account> accs = [SELECT Id, Name FROM Account LIMIT 3];
System.debug('Accounts found: ' + accs.size());

In the log, filter by USER_DEBUG to see your output.
